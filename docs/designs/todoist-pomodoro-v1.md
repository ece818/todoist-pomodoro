## Problem Statement

A Linux desktop Pomodoro timer glued to the Todoist task list. Pick a task, run the clock, mark it complete once, and Todoist reflects it. No double bookkeeping between timer and list. Built for self first, others later.

## What Makes This Cool

The desktop becomes the task: one giant fullscreen countdown with the task name huge, screen kept awake, sound, and a congratulations moment on completion. The user said it plainly: "i want to be able to show myself it and be excited to use it." Sync is table stakes; the ceremony is the product.

## Constraints

- Linux desktop first (repo: "Linux Desktop App For pomodoro timer connected to Todoist Tasks").
- The "keeps the phone unlocked" wish maps to desktop screen-awake: inhibit screensaver/sleep while the timer runs.
- Reference point: Focus To-Do on Android ("which is nice but it doesn't connect to todoist").
- V1 must be usable daily as fast as possible; stats and streaks wait.

## Premises

1. Linux desktop first. Fullscreen and screen-awake apply to the desktop via screensaver inhibit, not a phone. — agreed
2. Completion is explicit by the user and syncs to Todoist. Timer end and task-done are separate events; no auto-complete at timer end. — agreed. Concretely: at timer end the app stops, plays the end sound, and shows pause/reset/start-break options on the normal timer view. The congratulations moment and its big Complete button appear ONLY when the user declares the task done, never automatically at timer end. A short-break timer exists as a plain countdown without any task binding.
3. V1 = today's list (today + overdue, exact filter in Recommended Approach) + add task + timer + complete-sync + fullscreen countdown + sound + celebration. Stats/streaks deferred. Effort-log-back deferred (see Open Questions). — agreed
4. Single-user passion project first: a personal Todoist API token is fine for v1; multi-user auth later. — agreed

Synthesis: host and reviewer agree the ceremony (fullscreen, sound, celebration) is the delight core and completion must stay explicit. The reviewer added one idea the session missed: writing effort back into Todoist (`🍅 xN` per pomodoro) as a free effort log. No agreed premise was challenged, so premises stand.

Landscape note: phone/web/Mac Todoist timers exist (FocusFrog, PomoDial, Paslen, Pomist); PomoDial auto-completes at session end and Pomororo deliberately never touches tasks. Linux native timers (Tomate, Tomatillo, Tomatick, Tempus) have no Todoist sync found. The gap is real: Linux desktop + Todoist two-way sync.

## Approaches Considered

### Approach A: Minimal viable

Python + GTK4 single-focus app. Thin Todoist client (today, add, close). Today list + add-box + timer + explicit complete-sync + fullscreen countdown + sound + celebration. Fewest files, ships fastest.

### Approach B: Ideal architecture (chosen)

Same Python + GTK4 UI and thin Todoist client as A, but structured from the start: a separated sync layer (local state, explicit sync points, retry behavior), config handling, and packaging path (Flatpak) so the later multi-user story does not require a rewrite. Best long-term trajectory for something others will use later.

Today filter: the Today panel shows tasks due today plus overdue (Todoist "today" semantics: `due before tomorrow`), sorted overdue-first then by priority. No date-less backlog in v1.

Sync failure behavior: every add/close is idempotent from the UI side. On network or API failure the action stays visibly pending on the affected row (not a toast that vanishes), with a manual Retry affordance; automatic retry fires once when connectivity returns and on next app start. Sync error contract (per D11): 401 shows a re-token state and never retries; 429 honors Retry-After; every API call carries a timeout; transient failures retry with pending rows. Token storage (per D12): personal token in .env (gitignored, owner-only permissions); OS keyring deferred to sharing. Duplicate-close protection: the Complete button disables on first press until the close call settles, and close is reconciled against a fresh fetch before marking anything done locally, so double-clicks and restarts cannot double-close or fake a completion. Add idempotency (Outside Voice, High): every pending add carries a stable client-generated request ID, persisted with the pending row and sent as X-Request-Id on every attempt including reconnect and restart replays, so timeout-then-success can never double-create. Close stays safe via button-disable plus reconcile. Recurring tasks: Complete closes the current occurrence and Todoist schedules the next (occurrence-done, per D10).

### Approach C: GNOME Pomodoro base

Reuse GNOME Pomodoro's timer engine, break overlay, session inhibit, and sounds; build only the Todoist side panel + complete-sync glue. Least code if its extension points fit; dropped because plugin-internals friction is unknown and could stall a passion project.

## Recommended Approach

Approach B, because the user chose it and it fits the stated trajectory: build for self first, but architect the sync layer so "for people to later use" does not mean starting over. A stays as the fallback if B's structure slows down the first usable weekend.

## Open Questions

- Desktop environment target for inhibit/fullscreen APIs (GNOME first? which others matter?).
- Todoist auth for later multi-user: full OAuth flow deferred, but sync layer should not assume a single hardcoded token forever.
- Effort-log-back idea (`🍅 xN` notes on tasks): DEFERRED past v1 to keep scope closed. Revisit after v1 ships.

## Success Criteria

- "Done" = open the app each morning excited: see today's + overdue Todoist tasks, add one without leaving, run a fullscreen pomodoro that keeps the screen awake, hear the end sound at timer end, declare the task done to get the congratulations moment, hit complete once, and find it closed in Todoist.
- No second app open during a focus block.

## Distribution Plan

- V1: run from source on the user's own Linux machine. No packaging, no CI.
- Later: Flatpak packaging for sharing; CI/CD only when distribution starts. Deferred deliberately.
