## Problem Statement

V1 proved the loop: today's list, timer, complete-sync, stats. But every task operation beyond that still means opening Todoist: rescheduling, redating, quick capture with a date. V2 makes the app the only place task work happens: right-click any task for every action, drive everything from the keyboard, and type dates the way humans say them.

## What Makes This Cool

The mouse becomes optional and Todoist becomes invisible. Right-click a task and the full arsenal is there: start timer, complete, reschedule, change date. Ctrl+P does verbs, not just search. Typing "Call mom Mon 2pm" just lands on next Monday at 2pm. The user said it: "I want to not have to go into todoist to handle my apps, everything done in my app."

## Constraints

- Builds on shipped v1 (main): sync layer, error contract, pytest suite, GTK4 panels.
- In-app hotkeys are fully supported via ShortcutController; system-wide globals are impossible to grab on Wayland, so they arrive only as OS-registered shortcuts calling the `timer` CLI plus docs.
- Natural-language parsing is NOT built locally; Todoist's Quick Add endpoint parses server-side.

## Premises

1. V2 is an in-app command layer: right-click menu, deeper Ctrl+P actions, in-app hotkeys. True system-wide globals deferred to CLI hooks + docs. — agreed
2. Natural-language add uses Todoist's Quick Add endpoint (`POST /api/v1/tasks/quick`), which parses "Mon 2pm", #project, p1 server-side. No local NLP. — agreed
3. Full task powers live in-app: reschedule/redate via due_string update, complete, start timer. Todoist becomes the backup store. — agreed
4. V2 builds on the v1 sync layer, error contract, and test suite unchanged. — agreed

## Approaches Considered

### Approach A: Command layer on v1 (minimal)

Bolt a right-click menu and two palette actions onto the existing panels. Fewest files, ships fastest. Risk: menu, palette, and hotkeys each implement actions separately and drift.

### Approach B: Full command core (chosen)

One shared task-action service (start-timer, complete, reschedule, redate, quick-add) behind all three surfaces: right-click menu, palette verbs, hotkey map. Add-box replaced by a quick-add input speaking the Quick Add endpoint. Single source of truth for what each action does.

### Approach C: Palette-first

Rebuild Today around the palette as the primary interface. Most radical, most rework; dropped because today's panels work and users like them.

## Recommended Approach

Approach B, the user's pick: one action service so menu, palette, and hotkeys can never disagree. A stays as fallback if the service abstraction slows the build.

## Open Questions

- Exact hotkey map (which keys for start/complete/reschedule?) — must avoid entry-widget conflicts.
- Reschedule UX shape: preset chips (tomorrow, next week) vs free-text date entry vs both.
- Quick Add response parsing: confirm `POST /api/v1/tasks/quick` shape against the live API before building (the Assignment).
- CLI entry points for future OS shortcuts: which actions get `timer <verb>` first.

## Success Criteria

- "Done" = a full day of task work without opening Todoist: capture with "Mon 2pm", right-click to reschedule, Ctrl+P to complete, hotkeys for start/pause, stats still logging.
- No action exists in two surfaces with different behavior.

## Distribution Plan

- V1 path unchanged: run from source, `timer` launcher, no packaging.
- OS-shortcut docs ship with v2 as text; Flatpak still deferred.
